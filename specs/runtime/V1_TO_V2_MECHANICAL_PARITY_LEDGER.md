## 1. Current Truth Statement

Previous V1-to-V2 planning was not sufficient to prevent overbroad completion claims. This ledger is mechanical and evidence-based. A V1 capability is not considered migrated unless the exact V1 source/evidence, exact V2 implementation evidence, and exact V2 test/runtime evidence are all named and no required child behavior remains missing. V1 runtime evidence records 158+ clean routes, 746 collected tests, and a full run with 732 passed, 13 failed, and 1 skipped; the 13 portfolio-marker failures are exceptions, not positive proof. 02M remains frozen during this package. This file does not authorize implementation, does not claim V1 parity, and does not change the Master Sequence.

## 2. Status Definitions

### V2_EXISTS_VERIFIED

Allowed only when:

- the exact V1 capability/source is named;
- exact V2 implementation files, routes, components, models, or services are named;
- exact V2 tests are named;
- test/runtime evidence is named; and
- no known missing sub-capability remains in that row.

### V2_PARTIAL

Use when some V2 implementation exists but at least one required V1 sub-capability, test, route, UI flow, calculation, output, or integration is missing.

### V2_MISSING

Use when the V1 capability exists and no V2 implementation evidence exists.

### V2_REPLACED_BY_NEW_DESIGN

Use only when V2 intentionally implements the same business outcome differently, replacement files/tests are named, and missing V1 behavior is explicitly listed.

### V2_EXCLUDED_BY_DECISION

Use only when an explicit accepted V2 decision excludes the capability and the decision source is cited by file/path.

### UNKNOWN_NEEDS_INSPECTION

Use when V1 or V2 evidence is insufficient.

## 6. False Completion Guardrails

- A broad capability cannot be marked complete if any child row is `V2_PARTIAL`, `V2_MISSING`, or `UNKNOWN_NEEDS_INSPECTION`.
- "Fixation Rights" cannot be marked fully migrated if historical severance/grant indexation, 161D/output artifact, scenario integration, or external index source rows are partial, missing, or unknown.
- "Clearinghouse" cannot be marked complete if raw preservation, XML parsing, normalized staging, ledger promotion, and error handling are not all verified.
- "Tax engine" cannot be marked complete if annual parameters, external index data, prisa, marginal tax, and formula/golden cases are not verified.
- "Scenario engine" cannot be marked complete if scenario input snapshots, immutable runs, tax integration, annual/cumulative results, and comparison are not verified.
- "Reports" cannot be marked complete if output snapshot, renderer, PDF/export, source manifest, artifact storage, and redaction are not verified.
- A passing broad test suite does not replace a missing row-level test.
- A route name does not prove persistence, UI, calculation correctness, source trace, or artifact rendering.
- V1 planning/source presence does not authorize V2 implementation, and V2 planning presence does not count as implementation evidence.

## 7. Relationship to Master Sequence

- Every ledger row maps to at least one M01-M16 milestone in the table.
- Rows marked `V2_MISSING` or `V2_PARTIAL` become backlog inputs for the mapped milestone after this ledger and the Master Sequence are reviewed.
- `UNKNOWN_NEEDS_INSPECTION` rows require the named bounded inspection before parity status can be changed.
- The Master Sequence controls build order.
- The Parity Ledger controls whether V1 parity is actually achieved inside each milestone.
